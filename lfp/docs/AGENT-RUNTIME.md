# Agent runtime — how Bropilot's agents are built on Flue

Hand-written guide (not generated). Read this before touching anything under `agent/` or `src/agents.ts`. It records what we verified about `@flue/runtime` 2.0.6 (docs at `node_modules/@flue/runtime/docs/guide/*.md`) and the decisions taken on 2026-09-21. The table of agents itself lives in `src/agents.ts` and renders in-app and in `docs/AGENTS.md`; this file explains the why and the how.

## 1. The shape of the system

Three loops, each closed by a different party:

| Loop | Fails when | Raised as | Closed by |
|---|---|---|---|
| Meta (kernel constraints) | graph shape / cardinality / condition coverage broken | a **question** (`FollowUp.raisedBy.kind = 'violation'`) | the user answering through Talk |
| Representation → reality | a rule's condition has no fresh passing test | a **task** targeting the tests | a Builder agent in a sandbox, then a Reviewer |
| Clarification | an agent cannot derive a measurable "done" | a **question** (`raisedBy.kind = 'agent'`, task → `blocked`) | the user answering; the task resumes |

Everything an agent does to the graph goes through the commit gate (`stage` → approve → `commit`). The only exceptions are glossary edits and task state transitions.

**What a Talk turn costs (2026-09-28).** Answering is code, never a model turn. The Now strip (the top of `rankOpen()`) is the one place to act on the next open item: its Answer it + typed text (`forItem`) and its option buttons (a `choice` whose `forAsk` is an open item's id) both become an `answer` cue plus `link-answer` in `directors/index.ts::handleUser`; only choices on an `ask` cue reach the director. `next-decision` therefore only *says* the item ("Next: Gap: …") unless the item has its own options. One answer can stage several nodes of a non-singular kind: `store.ts::splitItems` splits on newlines or " / ", since the Talk input is one line. The "Deciding…" / "Asking the agent…" placeholders are `transient` say cues: shown on the strip, never written to the transcript. Every `snapshot` carries `sessionId` (persisted in the store, regenerated by Reset to seed) so the agent server can start a fresh conversation for a new design instead of remembering the wiped one.

## 2. What Flue gives us (verified against 2.0.6)

- **An agent is a function that returns its system prompt** and re-renders before every model turn. Hooks compose it: `useModel('provider/model', { thinkingLevel })`, `useTool(defineTool({...}))`, `useSandbox(adapter)`, `useSubagent({ name, description, agent, model?, thinkingLevel? })`, `usePersistentState(key, init)`, `useAgentStart/useAgentFinish`, `useMcpConnection`. (`guide/models.md`, `guide/tools.md`, `guide/subagents.md`)
- **Tiers are subagents — with a limit.** `useSubagent` adds a `task` tool; the parent model delegates by name. The child runs in a fresh context (inherits sandbox + workspace only, never the parent's history or tools), may use a different model and thinking level, runs in parallel with siblings, depth ≤ 4, and resumes from its own durable transcript after a crash. **Inside a delegate, `useModel`, `useSandbox` and `usePersistentState` throw** (verified, `guide/subagents.md`): its model comes from the definition, it shares the parent's sandbox, and it has no state of its own. So anything that needs its own sandbox or budget (builder, reviewer) is a **top-level agent** with its own conversation, started by a tool in Talk (`init(Builder, { id })`), not a delegate. Observer and planner are delegates.
- **Per-turn model choice.** `useModel` runs on every render, so an agent can escalate mid-conversation by reading `usePersistentState`. Tool subsets are just conditional `useTool` calls; the runtime tells the model when tools appear or disappear.
- **Keep the instructions byte-stable; put what changes in signals** (2026-09-28, measured). The system prompt re-renders every turn and anything in it that moves costs twice: Flue appends an `instructions` signal ("System instructions updated.") that the model answers with a paid turn, and the provider's prompt cache misses for the whole history behind it. So Talk's instructions hold only static text (spec header, `agent/prompt.md`, the clarifier paragraph, a paragraph saying what the signals are), and `useAgentStart` appends the per-turn facts after the user message with `ctx.append({ kind: 'signal', type, body, attributes })` (`reference/agent-hooks-api.md` useAgentStart): **`screen`** on every dispatch (the catch-up note for controls the user applied + the screen line), **`kernel`** and **`graph`** only when their hash differs from the one this conversation last saw (hashes in `usePersistentState('signals:seen')`, so they survive a restart and a new session starts empty). `graph` is `talk.ts::graphDigest`: node titles by kind with ids, then edges as `A —type→ B`, capped at 60 lines with a count of what was cut, so the model stops paying for `read_graph` by kind. The turn counter stays out of the prompt for the same reason (only the one-time STOP line depends on it). The `[turn]` log prints `sys=<hash>` from the in-process `turn_request` event: it must not change within a conversation.
- **Prompt cache.** Over OpenRouter with an `anthropic/…` model, pi-ai sends Anthropic `cache_control` breakpoints on the system prompt, the last tool and the last message (`@earendil-works/pi-ai/dist/api/openai-completions.js` getCompat `cacheControlFormat`, `applyAnthropicCacheControl`). The TTL is Anthropic's default 5 minutes; `PI_CACHE_RETENTION=long` in the environment switches to the 1 h TTL (`resolveCacheRetention`), which costs more per cache write (Anthropic prices 1 h writes at 2× base input vs 1.25× for 5 min) and pays off only when a user pauses more than 5 minutes between turns. We do not set it. `cacheRead`/`cacheWrite` from each `turn` event's usage are in the `[turn]` console line and in the `aicall` bus message. Measured on the 5201 test (Sonnet 4.6, 38-node graph): a conversation's first turn writes ~12.4k tokens ($0.025–0.048); every later turn reads 12–15k from cache and writes only the new tail ($0.005–0.007 each, $0.012 when a changed `graph` signal adds ~1.8k tokens). Because the instructions and tools are shared, a brand-new conversation (Reset to seed) already reads ~6.6k tokens from cache on its first turn.
- **Turn-ending tools.** A tool that returns `{ output, terminate: true }` ends the response once its batch settles (`guide/tools.md`), so the model does not pay for an empty closing turn. Talk's `ask` terminates (measured: the response settles on the ask, no further turn); `say` does not, because the model may stage or point after speaking, so a response that ends in `say` still pays one short closing turn (~$0.005, all cache reads). A batch terminates only if every result in it does.
- **The contract at the finish seam.** Talk's `useAgentFinish` appends one `contract` signal per dispatch when the response is about to settle without a successful say, ask, stage, answer or raise_question, sending the model back for one more turn. `server.mjs` keeps its text and delegate fallbacks as the second line.
- **Compaction on the cheap tier.** `applySpec(spec, { compactionTier: 'cheap' })` passes `useModel(model, { compaction: { model } })` (`CompactionConfig.model`); Talk uses it, so a history summary runs on Haiku, not Sonnet.
- **Durability.** Every submission is recorded before work starts and owes one terminal outcome (`completed | failed | aborted`); default 10 attempts, 1 h timeout, overridable per agent (`Agent.durability = { maxAttempts, timeoutMs }`). Persistence adapters: in-memory (default), `sqlite(path)`, custom; a DB adapter (Postgres) coordinates replicas. Sessions resume with `init(Agent, { id })`. One live owner per conversation; you cannot dispatch from one process and read the in-flight stream from another. (`guide/durability.md`)
- **Observability.** `observe(cb)` streams every event with correlation ids (`agentName, conversationId, submissionId, turnId, taskId`): `submission_settled` is the reliable terminal signal; `turn` carries `response.usage` (input, output, cache read/write, cost); `tool_start/tool`, `task_start/task`, `log`, `compaction`. This is where `AICall` records and budgets come from. (`guide/observability.md`)
- **Structured output** only on tools (`defineTool({ output: v.object(...) })`) and on `harness.prompt(text, { result: schema })`; the top-level reply is text. So every result we care about is returned through a tool, never parsed from prose.
- **Sandboxes.** `bash()` = in-memory emulated Linux (just-bash), rebuilt per message, good for data work; `local()` = host fs + shell, no isolation; remote adapters via `flue add sandbox <provider>` for **E2B, Daytona, Modal, Cloudflare Sandbox, Cloudflare Computer**, lazily created per agent instance and reconnected for durability. (`guide/sandbox*.md`, `ecosystem/`)
- **Deployment.** `vite build` with `@flue/vite` → `dist/server.mjs` standalone Node HTTP server, or Cloudflare Workers where each agent is a Durable Object. Clients use `@flue/sdk` `createFlueClient({ url, token })` against `https://host/agents/<path>/<conversation-id>`; streaming is HTTP GET with backoff; auth is bearer/headers, application-defined. No hosted Flue service, no agent registry, no agent-to-agent network calls. (`cli/`, `sdk/`, `ecosystem/cloudflare.md`)
- **Providers.** `'provider/model-id'` specifiers over anthropic, openai, google, bedrock, vertex, groq, mistral, openrouter, cloudflare (Workers AI, no key)…; keys from the environment only; custom providers via `setProvider(createProvider(...))`; no built-in fallback (the agent function decides).

## 3. The agents

Declared once in `src/agents.ts` as `AGENTS: AgentSpec[]` (field `hosting: 'top' | 'delegate' | 'path'` records the choice above) (Node-runnable, explicit `.ts` imports, provenance on every entry), rendered on the Reference page and emitted to `docs/AGENTS.md`. `agent/agents/<id>.ts` implements each one as a Flue function whose hooks are driven by the spec, so the spec is the single source of truth for model, tools, budget and checkpoint.

```ts
export interface AgentSpec {
  id: 'talk' | 'observer' | 'planner' | 'builder' | 'reviewer' | 'clarifier';
  version: string;
  purpose: string;
  tier: 'none' | 'cheap' | 'mid' | 'strong';       // resolved to a model id by TIER_MODELS
  thinkingLevel?: 'off' | 'low' | 'medium' | 'high';
  tools: string[];                                  // tool ids from agent/tools.ts and agent/agents/tools/*
  aiFunctions: string[];                            // ids from src/ai/registry.ts this agent is allowed to call
  sandbox: 'none' | 'bash' | 'local' | 'remote';    // remote = the configured provider (E2B first)
  trigger: 'user-turn' | 'event' | 'schedule' | 'delegate';
  checkpoint: 'commit-gate' | 'auto-stage' | 'clarify-block' | 'none';
  budget: { maxTurns: number; maxWallMs: number; maxCostUsd: number };
  runsIn: 'browser' | 'local-node' | 'cloud' | 'sandbox';
  source: Provenance;
}
// Provider decision (2026-09-21): OpenRouter. One key (`OPENROUTER_API_KEY`), every vendor's models
// reachable as `openrouter/<vendor>/<model>`, swappable per tier without code changes. Direct
// `anthropic/...` specifiers still work when ANTHROPIC_API_KEY is set — TIER_MODELS is the only place
// that knows which.
export const TIER_MODELS = {
  cheap: 'openrouter/anthropic/claude-haiku-4.5',
  mid: 'openrouter/anthropic/claude-sonnet-4.6',
  strong: 'openrouter/anthropic/claude-opus-4.6',
} as const;
```

Model slugs on OpenRouter must be checked against `https://openrouter.ai/api/v1/models` before first use; if a slug is missing, change it here only.

| Agent | Tier | Tools | Trigger | Checkpoint | Runs in | Notes |
|---|---|---|---|---|---|---|
| **talk** | mid | all Cue tools, `read_graph`, `read_open`, `task` (delegates) | user-turn | commit-gate | local-node (cloud later) | The one conversation the user has. Owns the subagents below. |
| **observer** | none → cheap | `run_checks`, `run_tests`, `read_graph` | event (commit) / schedule | none | local-node / sandbox | Runs `checkInvariants` and `npm run observe`; writes `reality.json`. No model unless summarising. |
| **planner** | mid | `read_graph`, `read_open`, `stage` | event (observer finding) | auto-stage | local-node | `unrealised-to-tasks` and `next-decision`. Never commits. |
| **builder** | mid (strong for tasks flagged hard) | sandbox fs, `bash`, `git`, `run_tests`, `raise_question` | delegate (queued task) | commit-gate after full suite green | sandbox | Work order = task + rule lines + tests/conditions + provenance quotes (`scripts/dispatch.mjs`). |
| **reviewer** | strong, thinking high | read-only diff, `read_graph`, `run_tests`, `verdict` | event (suite green) | commit-gate (task `done → verified`) | sandbox / cloud | `review-change`: does the diff serve the rule's intent, or only the test? Verdict `serves-intent | overfits | unclear`. |
| **clarifier** | mid (= talk) | `raise_question`, `ask`, `answer` | delegate (blocked task) | clarify-block | browser via talk | Not a separate process: the escalation path from builder/reviewer into Talk's `ask`. |

Rules of thumb (settled in the literature and in Flue's own `subagents.md`): one agent with many tools when the tools form one coherent skill (Talk's Cue protocol); a separate subagent when a phase needs another model tier, another tool surface, or must not see the parent's context (builder, reviewer).

### Advice routing and critique points (2026-09-28)

**Advice goes to the agent.** In a live session the founder typed "which of the three capabilities would you build first, and why?" and route-utterance picked `next-decision`, so the app answered "Next: Summarise it in a paragraph." route-utterance now offers an `agent` key for advice, opinions, comparisons and reasoning. The shared router (`src/directors/route.ts`) sends `agent` to the director's fallback: the Talk agent under the RemoteDirector, describe-screen under the ScriptedDirector. As a deterministic backstop, a `next-decision` answer on judgement text (why, which … would/should/first/better, should we, would you, recommend, compare, trade-off, worth) also goes to the fallback, unless the text says "next" without "why" ("what should I do next?" stays local). Exact commands are unchanged and never reach route-utterance.

**Critique points.** When a commit newly commits the answer to `q-outcome`, `q-capability` or `q-summary` under the RemoteDirector, `src/directors/index.ts` publishes, right after the commit's snapshot:

```ts
{ kind: 'critique', answerId, questionId, question /* the template prompt */, answer /* the answer text */ }
```

"Newly committed" means an answer that a committed node points at and that no earlier commit had committed, so an unrelated later commit, an undo and recommit, or a reload never repeats it. `agent/server.mjs` also keeps a `critiqued` set by `answerId` and drops a repeat. The server dispatches it as a Talk turn whose message is a note, not a user line:

> [Critique point after q-outcome — no user message. The founder just committed "…" as the answer to "…". Read the graph digest (the latest graph signal), name the weakest link in the design in 3 sentences or fewer, and stage the one change that fixes it in this same turn: stage first, then say once what you staged and why. If nothing is weak, say so in one sentence and stage nothing. Use only point, stage and say; call read_graph only if the digest cut off a node you need.]

Same static prompt, same signals, same tools, same say/ask dedupe. The commit changed the graph, so its digest hash differs and the `graph` signal rides this turn. HEADER_RULES carries a matching rule: a critique that recommends a change without staging it is incomplete. Under `FAKE_AI=1` (no Talk conversation) the service answers a critique with one canned say, which smoke checks.

**Turn reasons.** `[dispatch]` and every `[turn]` line of a Talk dispatch print `reason=user`, `reason=catch-up` (a user turn that also carried the since-your-last-turn note) or `reason=critique`, so a session driver can count them.

## 4. Checkpoints and blocking

- **Commit gate** is the proposal-object pattern: agents produce `stage` cues, the user approves. Same shape as LangGraph `interrupt()` before an approval node.
- **Stage cues are normalised** (v4.5, `director.ts::normaliseEffects`): an agent's effects arrive flat — `{op:'add-node', kind, title}`, `{op:'add-edge', src, dst, type}` (also `from`/`to`/`edgeType`), `{op:'update-node'|'remove-node', nodeId}` — and become Effect objects with ids; unknown kinds, edge types and node ids (not in the graph nor added in the same changeset) are dropped with a warning, and an all-invalid stage stages nothing and says so. The `stage` tool's schema enforces the flat shapes server-side. Code-built changesets (answer, link-answer, need repair) carry `answerId` on every effect and replace what is staged; an agent stage while the user's answer is staged appends to it. Live session 10 (2026-09-28) froze on `e.edge.src` of a `{from, to, type}` effect before this.
- **Clarify-block**: Flue has no interrupt primitive, but the submission queue plus `usePersistentState` gives one. The builder persists `{ waitingOn: followUpId }`, calls `raise_question` (task → `blocked`), and returns. When the user answers, Talk dispatches the answer to the builder's conversation id; the builder resumes from its transcript with the answer appended, no replay.
- **Ask vs act** (Horvitz): ask when exploration yields zero or several plausible readings, or when no measurable done-criterion can be derived from the rule lines and test conditions. A raised question names the subject nodes, what is missing, and the two or three readings considered.

## 5. Budgets, safety, audit

Wire these, do not invent them: `thinkingLevel` and model per subagent; `Agent.durability` for retries and wall time; `useSandbox` isolation for anything that writes files; tool allow-lists per `AgentSpec.tools`; `observe()` → every `tool`/`turn` event appended to the `AICall` log with cost, so the Reference scoreboard shows spend per agent version. Hard caps in `budget` are enforced in the agent function (count turns via persistent state; abort past `maxCostUsd`). Keys only from the environment (`.env`, gitignored): `OPENROUTER_API_KEY` is the one we need; `ANTHROPIC_API_KEY` is optional for direct calls.

## 6. Topology

**Now (prototype).** `npm run agent` = one Node process: the WebSocket relay on :5200 and the Flue runtime in-process (`start({ agents: [Talk] })`, sqlite persistence in `agent/.flue/*.sqlite`). Talk owns observer/planner as `useSubagent` delegates and runs builder/reviewer through its `dispatch_task` / `run_review` tools as their own conversations (`builder:<taskId>`, `reviewer:<taskId>`). Builder uses `local()` against a fresh `git worktree` of this repo; switch to E2B (free tier, Flue-verified adapter) the moment we want isolation. The browser stays on the bus protocol; the agent server is the bus's `agent` client. `observe()` logs to stdout and to the `AICall` log via the bus. When a snapshot carries a new `sessionId` (Reset to seed), the server calls `handle.abort()` on the previous `talk:<sessionId>` conversation before starting the new one: a durable abort of its running head and queue (`reference/agent-api.md` abort), so the old design's turn stops paying and does not resume after a restart; its pending `read()` rejects with outcome `aborted`, logged as one line. To test the server live without disturbing :5200, run a copy with the port and the sqlite path changed (never `agent/.flue`) and a small `ws` client acting as the main screen.

**Later (cloud).** Two equivalent paths, choose when needed:
- **Cloudflare**: agents as Durable Objects, state in Durable SQLite or Hyperdrive Postgres, builder/reviewer sandboxes on E2B or Cloudflare Sandbox, tracing via `createCloudflareTracing()`, schedules via Cron Triggers. Lowest ops.
- **Node on Fly/Render**: one long-lived server, Postgres for durable queues, E2B or Fly Machines for sandboxes, `observe()` → OpenTelemetry.
In both, the browser talks to the runtime with `@flue/sdk` over HTTPS and the relay disappears; the Cue protocol stays.

**Sandbox choice.** Prototype: `local()` on a worktree, then E2B (2–5 s start, per-instance persistence, env-injected keys, free tier). Later: E2B for short tasks, Fly Machines when a workspace must persist across hours.

## 7. The browser ↔ runtime seam (`runtime: 'flue'`)

`src/ai/runtime.ts::runAI` is the only caller of any AI function. Its `flue` branch must not know about Flue: it calls an `AIBackend` interface (`src/ai/backend.ts`: `run(fnId, prompt, contextText, inputText, outputSchema) → Promise<unknown>`) with two implementations — `StubBackend` (today's deterministic stubs, synchronous) and `BusBackend` (publishes `{ kind:'ai-request', id, fn, prompt, context, input }` on the bus and awaits `{ kind:'ai-response', id, output | error }`). On the agent server, `agent/ai-service.ts` answers those requests with `harness.prompt(text, { result: schema })` on a cheap/mid model chosen from the function's registry entry, so every registry function gets a real model with **the same prompt, the same declared context and the same `toCues`** as the stub. The `AICall` record gains the model id and cost from the `turn` event. Switching `state.aiRuntime` in the Reference page flips backends live.

Implementation facts (Stage 3, verified; reshaped 2026-09-28): the server runs each request as a one-shot `AiFunction` agent whose dispatched message is the request's prompt and whose only tool is `result`, with input `{ result: <output schema> }` (wrapped because output schemas include `v.variant` unions and a tool input must be a top-level object) and a `terminate: true` return. A request is therefore **one model turn** (measured: find-gaps on Haiku, 1 turn, ~1.6k in, $0.003–0.004). The earlier `run_prompt` harness tool around `harness.prompt(text, { result })` cost three: the call to the tool, the scratch prompt, and a closing "then stop" turn. A model that answers in prose gets one `contract` signal from `useAgentFinish` and a second turn; failing that, the request errors and the browser shows the stub. Thinking is `'off'` (Flue's default when `useModel` names none is `'medium'`); `src/ai/registry.ts` has no tier or thinking field, so the exceptions live in `ai-service.ts::THINKING_BY_FN` keyed by fn id (today `review-change: 'low'`), next to `MID_TIER_FNS`. Usage is summed over every AiFunction turn while the request is in flight (the `turn` event's `conversationId` is Flue's internal `conv_…` id, not the instance id) and logged as `[ai-request] <fn> done: turns=… cost=…`. A Valibot schema is not JSON-serialisable, so it cannot ride Flue's durable `initialData` and travels through a module-level slot instead — which is only safe because `agent/ai-service.ts` drains requests **one at a time**. Give each request its own closure before adding concurrency. `FAKE_AI=1` answers the three smoke functions with canned, schema-valid output and never touches Flue, so the seam is tested in CI without a key. On timeout or schema failure the browser shows the stub result and marks the call `failed`; nothing blocks.

## 8. Decisions (v4.2)

- **Planner stays a Talk delegate.** No schedule trigger exists yet to justify its own conversation; revisit only when it needs one.
- **Reviewer precheck is rule-based, not a model call.** `agent/agents/precheck.ts::precheckDiff(changedFiles, codeRefs)` is a pure function: a changed file is in scope when it sits at or under the repo-relative path of at least one target's `props.codeRef`. `talk.ts::run_review` runs it before dispatching the reviewer — `git diff --name-only` in the worktree (`agent/agents/tools.ts::diffChangedFiles`, reusing the same allow-listed `repo diff` command) against the task's codeRefs. In scope (`scopeOk:true`) → the reviewer runs at **mid** tier; anything outside → **strong**. The tier is threaded in without changing `Reviewer()`'s signature: `run_review` sets the `TIER_OVERRIDE_REVIEWER` env var right before `init(Reviewer, ...)` and clears it after — `from-spec.ts::modelFor` checks `TIER_OVERRIDE_<SPEC_ID>` ahead of the spec's own `tier`. Once the reviewer calls `verdict`, `run_review` appends `{ verdict, reasons, at, scopeOk }` to `src/reality.json.verdicts[taskId]` itself (it already runs server-side) and publishes a `reality` bus message the browser does not yet handle.
- **The task lifecycle gate reads that verdict.** `checks.ts` raises `task-done-without-verdict` (question) when a task is `done`/`verified` with no verdict recorded, and `task-verified-without-green` (task) when a task is `verified` but not every targeted test is pass-and-fresh — `store.ts::applyReality` sets `props.verdict` and moves `done → verified`/`blocked` before `checkInvariants` runs, so both checks read the merged graph, never `reality.json` directly.
- **Cloud path deferred.** Cloudflare vs. Node stays undecided until the first non-local user appears; nothing here depends on the choice yet.
- **Every violation follow-up is a need repair, answered in code (v4.4).** `store.ts::answerFollowUp` takes what an option does from one table, `checks.ts::OPTION_ACTS` (link / add / defer / remove), and the edge to stage from `checks.ts::repairOf` (the kind's `needs` row, a `verifies` test for a rule condition, or the `LINKS` rules for an orphan). An existing title of the needed kind stages only the edge, a new title stages the node and its edge together, a deferral ("Mark as intentionally absent for now", "Defer", "Leave as a stub") stages and answers nothing, and a bare "Add one" only says what to type, so a repair label never becomes a node title. Needs offer the needed kind's titles like orphans, and wait for the template question producing that kind (a bet asks for a metric once q-metric was answered or a metric exists). `rankOpen` puts a follow-up about the latest answer's committed nodes ahead of the next template question. q-summary now comes last, after q-capability, and q-assumption after q-hypothesis.

## 9. System One (v4.3): classification goes to Jev, strings stay with code

**What it is.** TypeSafe's Jev is a "System One" model: state in, typed answers out (`choice` over a fixed set, `score` on an ordered scale, `noul` yes/no probability), every question in a request answered in one parallel pass, calibrated confidence on each, ~0.1–0.5 s, $0.042 per million input tokens. It generates no text, cannot count, reads literally, and degrades as irrelevant state is added. So the rule for what moves to it: **a decision whose valid answers can be listed in advance and whose wrong answer is cheap to catch**. Routing, "which node does this text name", "do these two lines contradict", "are these two titles the same thing", the three-way review verdict, the reviewer tier, edit-vs-new, "can a measurable done be derived", and "does test condition X verify rule line Y". Nothing that produces a string (`raise-question`, `propose-followup`, `walk-map`, the consolidated prompt) and nothing structural (edge shapes, cardinality, the lifecycle gate) moves.

**One seam, no new process.** The key stays on the agent server: `TYPESAFE_API_KEY` goes direct, otherwise the `OPENROUTER_API_KEY` the Talk agent already has reaches the same System One endpoint on OpenRouter (`/api/v1/systemone`, model `typesafe/jev-1.13`, cost on the response) through the same SDK with a base-URL change. The browser builds the SDK's own question shape and ships it over the bus as `system1-request { id, fn, state, questions }`; `agent/system1-service.ts` answers with `system1-response { id, answers | error, model, ms, usage }`. `agent/system1.ts` is the only file that imports `@typesafe-ai/sdk` (lazily; pinned to `jev-1.13.0`); if the early-access API moves, that file changes and nothing else does. At connect and on every main-screen `hello` the server publishes `system1-ready { ready, mode: 'live' | 'fake' | 'off' }`; the browser mirrors it into `state.system1Ready`/`state.system1Mode`. `FAKE_S1=1` answers from a canned table and never imports the SDK: every noul is a confident yes, every choice the first key, every score the top level — unless the request's state contains `#s1no` (noul false / choice `none` or last key / score 0) or `#s1low` (low confidence). Smoke plants those tokens in a node title or an utterance to drive both branches of every gate without a second server.

**Orthogonal toggle, not a third runtime.** `state.aiRuntime` stays `'stub' | 'flue'` for generation. `state.system1` (Reference checkbox, default on, effective only when `system1Ready`) says whether decision-bearing functions ask Jev first. A registry function opts in by declaring `decision: DecisionSpec` next to `stub`/`toCues` (`src/ai/types.ts`): `questions(input, ctx)` returns `{ state, questions }` or `null` (nothing worth asking — use the stub), `decide(answers, input, ctx)` makes the final output from typed answers in code, `confidence(answers)` optionally replaces the default "weakest answer" rule (find-contradictions uses the mean so one borderline pair does not discard a batch). `src/ai/runtime.ts::runDecision` takes the flue branch's shape — placeholder cue, real cues when the answer lands — but **a fallback is never a failure**: below threshold, timeout, error, or nothing-to-ask all run the stub, i.e. exactly the pre-v4.3 answer, and the `AICall` stays `ok` with `runtime: 'stub'` and `fallback: 'low-confidence' | 'timeout' | 'error' | 'nothing-to-ask'`. A Jev-decided call records `runtime: 'system1'`, `confidence`, `model`, `costUsd`. `AIFunctionMeta.hasDecision` is the Node-visible flag (`docs/AI-FUNCTIONS.md` "System One" column); do not add a third roster next to `MID_TIER_FNS`.

**Thresholds live in one file.** `src/ai/decisionConfig.ts` (Node-runnable, shared by browser, server and scripts): route-utterance .70, find-by-title .65, duplicate-detect .80, find-contradictions .75, review-change .80, reviewer-tier .70, edit-vs-new .70, ask-or-act .85, condition-match .85, consolidate-pair .75, raise-parent .65, link-answer .60 (its single-target choice), link-answer-pair .55 (each pair noul). A noul's confidence is `|p − 0.5| · 2`. Tune from the Reference call table (approval rate by runtime), not by feel.

**State shaping rule** for every `questions()`: send only the literal strings the question needs — titles, condition lines, the user's text, and flags computed in code (e.g. per-condition exact-match coverage for `review-change`). Never the graph, the transcript, a description the question is not about, or anything that needs counting or a second lookup. Code pre-filters candidates (`src/ai/candidates.ts::titleCandidates`, the contradiction regex pre-filter, near-miss title pairs); Jev picks.

**Where it acts.**
- Talk router: every regex branch in `directors/route.ts` (the `Router` shared by the Scripted and Remote directors) is untouched and instant; only fall-through text asks `route-utterance` (an `internal` registry function whose `toCues` is empty — the function it dispatches produces the cues). Below threshold → `describe-screen`, today's behaviour.
- Browser functions with a `decision`: describe-screen, explain-node, find-contradictions, define-term, review-change, answer-to-effects.
- link-answer (edges for a just-staged answer's new nodes, `src/ai/links.ts` LINKS, derived from `kernel.ts` RELATIONS since v4.5, see below): context, usecase, problem ←has— audience (many); problem ←has— usecase (many); outcome ←motivates— problem (many); hypothesis —references→ outcome (one) and —references→ metric (many); assumption —references→ hypothesis (one); metric —monitors→ outcome (one) and ←references— hypothesis (many, so answering the metric question links the committed bets it measures); capability —satisfies→ problem and —satisfies→ usecase (many). It gates **per answer** (`DecisionSpec.gate: 'answer'`, no call-level fallback): a `many` rule asks one `noul` per (new node, candidate) pair with a literal question (`Does the audience "A" have the context "X"?`) and structured criteria (`{ true: { definition, examples }, false: { … } }`); a pair links when its own confidence clears `link-answer-pair` (.55) with p ≥ .5, is dropped when it clears it with p < .5, and is *uncertain* otherwise. A single-target rule asks one `choice` over the candidates + `none`, gated on its own confidence against `link-answer` (.60), a separate key because a noul threshold does not carry over to a choice. The stub links only a lone candidate, never all-to-all (live 2026-09-28 it linked every candidate on 6 of 7 fallbacks, about 27 of 30 edges noise). The note counts what is still open: "linked 2 of 3 new nodes; 1 needs you". Whatever still lands as an orphan gets a follow-up whose options are up to 6 titles of the rule's target kind plus Remove it and Leave as a stub; `store.ts::answerFollowUp` stages the picked title's edge (or a remove-node, or defers) in code, with no model call. A node that got some edges but kept uncertain pairs is asked by a link follow-up (below).
- Server gates: `run_review` asks one `score` (routine → high-risk) from file count, `scopeOk`, extra file paths and the targeted test/rule titles — never the diff — and `precheck.ts::tierFor(scopeOk, risk)` picks strong when out of scope or when a confident score reaches "sensitive"; the verdict record gains `risk`. `scripts/dispatch.mjs` asks one `noul` ("can a measurable done be derived from these lines?") before writing a work order; a confident no writes the question to `reality.json.raised[taskId]` and sets the task `blocked` in `graph.json` instead of writing a work order (`--no-gate` skips it); `store.ts::applyReality` turns each `raised` entry into the same agent-raised follow-up the `raise` cue makes, so it shows in the Talk panel at the next load.
- Observe-time cache: `scripts/observe.mjs` asks one `noul` per (rule condition, test that verifies the rule) pair that is not already string-equal and writes `reality.json.matches[contentHash(cond)][testId]`; `checks.ts::checkInvariants(graph, { matches })` counts a cached probability ≥ threshold as covered. Only `store.ts` passes the table. The same pass cross-checks the two structural decisions that stay in code — `groupViolations` pairs (consolidate-pair) and `parentFor` (raise-parent) — into `reality.json.decisions[id]` with `agreedWithCode`; Reference shows counts, mean confidence and % agreed (`ref-decisions`) so the numbers exist before those ids are handed over. `S1_SKIP=1` skips the pass, `S1_ONLY=1` runs only it.

### Design spine relations and link follow-ups (v4.5)

**One table.** `src/kernel.ts` RELATIONS lists the design spine as explicit rows: (src kind, edge, dst kind, `many`, `at`, `need`). Everything that used to be hand-written separately is derived from it. `ai/links.ts` LINKS holds the rules link-answer proposes when a node arrives, taken from each row's `at` end. `linkRulesFor(kind)` holds every row touching a kind, which is what orphan repair offers. A row with `need` becomes the src kind's `needs` entry, so the bet-needs-a-metric check comes from the table. It keeps the existing gating: a need fires only once its kind's question was answered or a node of it exists. The non-template kinds (module, rule, protocol, test, task) keep their `needs` inline in KINDS. EDGE_TYPES stays the shape vocabulary. `TEMPLATE_ORDER` replays `nextQuestion` over QUESTIONS. At module load, outside a production build, kernel.ts asserts two things per row. The row must be admitted by EDGE_TYPES. Its `at` must be the later-asked end, or `both`, so link-answer always has candidates when a node arrives. Problem is asked before outcome, so outcome ←motivates— problem is proposed at outcome time. Only hypothesis —references→ metric is `both`, because a new bet after metrics exist should link too.

**Uncertain pairs get asked.** link-answer's `uncertain` (node → candidate ids nobody decided) goes to `store.ts::noteUncertain` from its `toCues`. A node still in the staged changeset waits for `commit()`. A node already committed is asked at once. Each uncertain node gets one follow-up, `f-link-<nodeId>`, with `raisedBy.kind: 'link'`, deduped on id. Its prompt is `Does "<title>" relate to any of these? Pick the one that applies.` Its options are the uncertain candidates' titles plus "None of these", and its subjects are the node then the candidates. **One pick answers it**, the simpler design, because options are single clicks. A picked title goes through the need-repair staging path (`stageLinks`), restricted to the candidates, and stages that edge. Several titles typed with " / " stage each. "None of these" or "Done" answers it with nothing staged, which is not a defer loop. Ranking: while the node is from the latest committed answer, the follow-up sits right after the fresh-violation tier and before the next template question (tier 3). Otherwise it is tier 4. It is hidden while the node's own orphans follow-up is open, since that one already offers the titles. `syncRaised` drops an unanswered one when the node is removed, gains an edge to any candidate, or loses every candidate. A discarded changeset clears the pending set.

### Chained questions over the ontology (2026-09-28)

A flat question fails in the two ways Jev's own docs warn about. A large mixed option set puts "Reviewer" the agent next to "Review change" the ai-function. A shared state full of things the question is not about drags every answer toward "no". The fix is the kernel's own ontology, used as a question tree in `src/ai/ontology.ts` (Node-runnable, imports only `kernel.ts`): layer → space → kind → node for "which node does this text name", and subject → invariant → repair for "do these two gaps belong together".

The design rule:
- **Small homogeneous option sets.** One level of the ontology per question, never nodes of every kind in one choice.
- **Ground each level with the level below.** Every kind option carries three example titles from the graph. Singular kinds (name, purpose, summary) are left out; left in, they were the sink for every vague phrase.
- **Siblings in one request.** Jev answers every question in a request in one parallel pass and output tokens are free, so code asks every branch at once and reads only the chosen one.
- **Dependent levels cost one round trip each.** `DecisionSpec.next(answers, input, ctx)` returns the next request or `null`; `system1.ts::decideGated` walks at most 4 levels and merges the answers before `decide()` runs.
- **Code walks the tree.** Jev never sees the tree; code picks the branch, combines the levels and computes the confidence.

**Where it is used.** describe-screen and explain-node (for bets) ask the substring candidates, when any, side by side with "which kind of item?". A candidate answer at or above the find-by-title threshold ends the chain; otherwise level 2 asks "which node of that kind?" with `none`. The consolidate-pair cross-check asks three nouls per pair: same item? same kind of thing missing? one combined question? The literal violation messages and subject titles go in the instructions and the shared state is empty. Together means repair ≥ .5 and (subject ≥ .5 or missing ≥ .5); confidence is the minimum. raise-parent asks the space and the question-within-each-space in one request. `observe.mjs` records the chained verdict object as `value` for consolidate-pair and the chosen `space` for raise-parent.

**Measured** (`npm run s1:eval [-- node|gaps|parent]`, live; direct TypeSafe key, ~250 ms per level):

| Decision | Variant | Result |
|---|---|---|
| Node by text, 20 labelled phrases over the seed graph | substring candidates only | 6/20 |
| | kind → node, no examples | 12/20 |
| | space → kind → node, with examples | 15/20 |
| | **kind → node, with examples** (shipped) | **17/20**, mean confidence 0.77 |

The chain now resolves paraphrases with no substring hit, such as "the phone view", "the websocket relay" and "the PR gate protocol". The three node misses are genuinely ambiguous: "the glossary" lands on asset, "domain modelling" on term, "the one-thing-at-a-time companion" on agent. The gap levels read correctly. Invariant groups score subject 0.03, missing 0.95, repair 0.86; subject groups score 0.69, 0.94, 0.86. The 8 raise-parent disagreements are all reality-layer kinds (test-result, metric-reading, evidence and similar). There Jev picks q-metric "How will you know?" over the code's q-capability fallback, and Jev is arguably right; this is an open question and `parentFor` is unchanged.

**The wording lesson.** The third gap level first asked whether "one sentence resolves both". For invariant groups Jev honestly said no, because each hypothesis needs its own metric. What consolidation actually means is "one combined question the user answers in a single reply", and that wording gives the 0.86. Ask Jev the question the code means, in the words the user will see.
